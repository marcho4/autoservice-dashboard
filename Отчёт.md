# Дашборд заявок для автосервисов

## Доменная область

Cервисы тех. обслуживания автомобилей. Заявки приходят в Телеграм или WhatsApp, мастера долго не могут ответить, заявки теряются, клиент уходит к конкуренту. Мое приложение помогает увидеть свои заявки на дашборде. ТГ бот не входит в приложение, приложение предоставляет REST API для интеграции с ботом.

## Сущности

Автосервис, сотрудник автосервиса, клиент, заявка, бот-раннер, система

## Стэк

Go для backend, chi - библиотека роутера, Next.js - фронтенд, PostgreSQL база данных, JWT для авторизации/аутентификации, Docker для контейнеризации

## Аргументация 12 пунктов

1. Кодовая база в одном месте: наличие единого гит репозитория
2. Зависимости: для Go есть go.mod, для next.js - package.json
3. Конфигурация в окружении: все приложения настраиваются через переменные окружения. В частности конфигурируется то, что меняется между окружениями.
4. Сторонние службы: в PostgreSQL приложение ходит через адрес, который передается в окружении под переменной
5. Сборка, релиз, запуск: каждый компонент системы собирается в докер образ. Релиз = набор переменных окружения и сборка докер образа. Запуск осуществляется просто созданием и запуском докер контейнера с определенными переменными окружения.
6. Привязка портов: приложение самодостаточное и само реализует HTTP сервер на порту, который передали через окружение. Справедливо для фронтенда и бэкенда.
7. Процессы: приложение исполняется в едином процессе. Весь стейт, который должен сохраняться между перезапусками, хранится в PostgreSQL. Процессы являются stateless и не пишут ничего на локальный диск.
8. Параллельность: Приложение масштабируется горизонтально запуском нескольких экземпляров процесса
9. Утилизируемость: бэкенд на Go при получении SIGTERM делает Graceful Shutdown, завершая все текущие функции корректно
10. Dev/prod паритет: тестовое окружение использует тот же стек, что и продовое. Docker образы совпадают в test и в prod
11. Логгирование: Приложение не отвечает за хранение логов. Все логи пишутся в stdout в едином формате
12. Администрирование: В контексте приложения все администраторские задачи, как применение миграций, рестарты и тд происходят одной командой через бинарник приложения (например `docker compose run --rm api ./app migrate` ).
Это исключает расхождение между кодом приложения и кодом административных скриптов.
