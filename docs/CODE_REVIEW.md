# Ревью бэкенда и фронтенда

Дата: 14 ноября 2026 года. Изначальное ревью: `84e7133`, с удалёнными комментариями. Все четыре замечания ниже исправлены; описание проблем и номера строк в них относятся к состоянию до исправлений.

## Результат исправлений

1. Telegram-обновления сохраняются в таблице `bot_updates` до продвижения `offset`. Необработанные сообщения восстанавливаются после перезапуска, ошибки обработки повторяются; идентификатор последнего обработанного обновления записывается вместе с состоянием диалога, чтобы повторная доставка не меняла ответы второй раз. Очередь по-прежнему обрабатывает разные чаты параллельно. Нужна миграция `0003_bot_updates.sql`.
2. Создание сотрудника, автосервиса и стартового каталога выполняется в одной транзакции. Ошибка любого этапа откатывает регистрацию целиком, после чего тот же email можно использовать повторно.
3. Успешное сохранение заметки очищает черновик только при совпадении с отправленной версией. Более новые правки сохраняются, а сообщение «Заметка сохранена» не показывается для несохранённого текста.
4. Эффект загрузки заявок игнорирует как успешные ответы, так и ошибки запросов предыдущего фильтра, страницы или сортировки.

Регрессии проверяются постоянными тестами: откат регистрации при ошибке автосервиса и каталога, сохранность очереди при остановке, отсутствие подтверждения Telegram при ошибке записи входящего обновления, защита от повторного обновления диалога и три браузерных сценария Playwright.

What this change does: В репозиторий установлены `ponytail` и `ponytail-review` из официального [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail), коммит `96608e078b2d5ea607c5c3b8b5a54d1c1fba6846`. Удалены 366 поясняющих комментариев из 59 файлов бэкенда и фронтенда, включая тесты, SQL, CSS и конфигурацию фронтенда. Исполняемые токены Go и JavaScript, полученный из TypeScript/JSX, остались прежними.

Ревью охватывает HTTP API, авторизацию, сценарии регистрации и заявок, PostgreSQL-репозитории, обработку сообщений Telegram, API-прокси и основные страницы кабинета. Ожидаемый режим — несколько пользователей одновременно, две реплики бэкенда и фронтенда из `deploy/deployments.yml`, один лидер Telegram-раннера.

## Исходные замечания

1. **[P1] Telegram подтверждает сообщения до их обработки** — `backend/internal/bot/runner.go:236–249`, также `:188–195` и `:218`.

   **Что это:** раннер получает обновления, ставит обработчики в очередь в памяти и сразу передаёт следующий `offset` в `getUpdates`. Telegram после этого считает предыдущие обновления доставленными.

   **Проблема:** обработчик ещё может ждать LLM или базу, когда сообщение уже подтверждено. При остановке очереди пропускают ожидающие задачи через `ctx.Err()`, а выполняющиеся отменяются после `HandleGrace`; при аварии очередь также исчезает. Сообщение больше не доступно для повторной доставки, хотя состояние диалога или заявка ещё не записаны.

   **Исправление:** подтверждать только непрерывную последовательность успешно сохранённых обновлений. Самый простой вариант для текущего продукта — завершать обработку пакета до следующего опроса и возвращать результат обработки; если нужна независимая параллельная обработка чатов, сначала сохранять входящие обновления в PostgreSQL.

   **Если пропустить:** перезапуск, смена токена или сбой могут потерять ответ клиента либо подтверждение заявки. Воспроизведено на фейковом Telegram: загрузка диалога заблокирована, `Pending()` уже равен нулю; остановка раннера отменяет обработчик, ответ не отправлен, повторной доставки нет.

2. **[P2] Регистрация записывает сотрудника и автосервис раздельно** — `backend/internal/usecases/auth.go:67–74`.

   **Что это:** регистрация владельца создаёт аккаунт и его автосервис, после чего выдаёт сессию.

   **Проблема:** `employees.Create` фиксирует аккаунт до `autoservices.Create`. Если второй запрос завершается ошибкой, клиент получает HTTP 500, но аккаунт уже существует. Повторная регистрация с тем же email получает HTTP 409 `email_taken`.

   **Исправление:** создавать сотрудника, автосервис и стартовый каталог в одной транзакции PostgreSQL. Текущая транзакция внутри `AutoserviceRepo.Create` не включает создание сотрудника.

   **Если пропустить:** временный сбой оставляет незавершённую регистрацию, и повторная попытка не помогает. Воспроизведено на отдельной базе: триггер отклонил вставку автосервиса; после HTTP 500 остался один сотрудник и ноль автосервисов, повторный запрос вернул HTTP 409. Вход через отдельную страницу остаётся возможным, но пользователь не получает предусмотренного завершения регистрации.

3. **[P2] Сохранение заметки стирает более новые правки** — `frontend/app/(dashboard)/requests/[id]/page.tsx:40–44`, поле ввода `:130–144`.

   **Что это:** заметка сохраняется запросом к API, при этом пользователь может продолжать вводить текст.

   **Проблема:** отправляется версия А; пока запрос выполняется, пользователь дописывает версию Б. Ответ содержит А, а безусловный `setNote(null)` сбрасывает локальную Б и показывает «Заметка сохранена».

   **Исправление:** сохранить отправленную версию в локальной переменной и очищать черновик через функциональное обновление состояния только если текущий текст всё ещё совпадает с отправленным. Сообщение об успешном сохранении также должно учитывать наличие более нового черновика.

   **Если пропустить:** пользователь теряет введённый текст и получает ложное подтверждение его сохранения. Случай подтверждён исполнением извлечённой из исходника `saveNote` с управляемым завершением API-запроса.

4. **[P2] Запоздавший ответ API подменяет выбранный фильтр заявок** — `frontend/app/(dashboard)/requests/page.tsx:41–51`.

   **Что это:** смена статуса, сортировки, страницы и автоматическое обновление запускают загрузку списка заявок.

   **Проблема:** эффект не отменяет старую загрузку и не проверяет, актуален ли её ответ. Если запрос «Все» завершается после запроса «Новые», вкладка остаётся «Новые», а таблица показывает результат «Все». Аналогично могут перепутаться страницы и сортировка.

   **Исправление:** возвращать из эффекта очистку с флагом актуальности и проверять его перед `setData` и `setError`. Альтернатива — отменять предыдущий запрос через `AbortController`, передав его сигнал в общий API-клиент.

   **Если пропустить:** сотрудник видит данные, не соответствующие выбранному фильтру, до следующего успешного обновления. Воспроизведено исполнением исходного эффекта: новый запрос завершён первым, старый вторым; итоговое состояние содержит старый список.
