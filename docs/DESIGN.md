# Проект системы: заявки автосервиса из Telegram

Статус: v2, оценка пройдена. Решения по её итогам — в разделе 11.

## 1. Зачем это

Мастер в небольшом автосервисе занят машиной и не отвечает на сообщения. Клиент ждёт, не дожидается и уходит
к конкуренту. Продукт принимает заявку за мастера: бот в Telegram выясняет, что нужно клиенту, и кладёт готовую
заявку в кабинет. Мастер перезванивает, когда освободится.

**Цель MVP.** Владелец регистрируется, вставляет токен бота — и больше ничего не делает: бот принимает заявки,
они видны в кабинете.

**Что не входит в MVP.** Запись на конкретное время и расписание, оплата, несколько сотрудников с ролями,
переписка с клиентом из кабинета, WhatsApp и другие каналы, ответы бота на произвольные вопросы.

## 2. Кто пользуется

| Роль | Что делает | Где |
| --- | --- | --- |
| Владелец | Регистрирует автосервис, подключает бота, настраивает услуги | Кабинет (браузер) |
| Мастер | Разбирает заявки, перезванивает клиентам | Кабинет, чаще с телефона; уведомления в Telegram |
| Клиент | Описывает задачу и оставляет телефон | Telegram, чат с ботом автосервиса |

В MVP владелец и мастер — один аккаунт кабинета. У одного аккаунта один автосервис, у автосервиса один бот.

## 3. Главные сценарии

**Онбординг владельца.** Регистрация (название автосервиса, имя, email, пароль) → экран «вставьте токен из
@BotFather» → токен проверяется в Telegram → бот запускается → экран «бот работает» со ссылкой на бота.
Типовые услуги уже созданы, поэтому бот полезен сразу.

**Заявка клиента.**

1. Клиент открывает бота: «Здравствуйте! Чем могу помочь?»
2. Клиент пишет своими словами: «Хочу поменять масло на камри 2015, пробег 120 тысяч».
3. LLM определяет услугу и поля формы, которые клиент уже назвал.
4. Бот задаёт только недостающие вопросы формы — по одному, без LLM.
5. Бот спрашивает телефон (кнопка «Отправить мой номер» или текст).
6. Бот показывает заявку целиком. Клиент нажимает «Отправить», «Изменить» или «Отменить».
7. Заявка появляется в кабинете; подписанным мастерам приходит сообщение в Telegram.

**Разбор заявки мастером.** Список заявок → карточка → «Взять в работу» → звонок клиенту → заметка →
«Закрыть». Статусы: `new → in_progress → closed`, `new → rejected`; клиент может отменить новую (`cancelled`).

## 4. Архитектура

```
 Telegram ──long polling── Раннер ботов ── Диалог (FSM) ── LLM (OpenAI-совместимый API)
                               │                │
 Браузер ── Next.js ── HTTP API (Go) ───────────┴── PostgreSQL
```

Один Go-бинарник с командами `serve` (HTTP API и раннер ботов), `bot` (только раннер), `migrate`, `probe`.
Фронтенд — Next.js, ходит в API через свой серверный прокси; JWT лежит в httpOnly-cookie.

Слои бэкенда: `domain` (сущности и правила) → `usecases` (сценарии) → `adapters/httpapi`, `bot` (вход) и
`gateway/*` (PostgreSQL, Telegram, LLM). Зависимости направлены внутрь, внешние сервисы закрыты интерфейсами.

**Почему раннер внутри `serve`.** Один контейнер — весь продукт: меньше, что разворачивать и что может быть
забыто. Раннер можно вынести командой `bot`, не меняя кода.

**Почему long polling, а не вебхуки.** Не нужен публичный HTTPS-адрес и его настройка для каждого бота. Цена —
один долгий запрос на бота и ровно один опрашивающий процесс.

## 5. Данные

| Таблица | Содержит | Заметки |
| --- | --- | --- |
| `employees` | Аккаунты кабинета | bcrypt, версия токена для отзыва сессий |
| `autoservices` | Автосервис, счётчик номеров заявок | один на аккаунт |
| `services` | Услуга: название, описание для LLM, порядок, включена ли, форма | форма — JSON-массив полей |
| `bots` | Токен, статус раннера, код ссылки мастера | один на автосервис; токен уникален между автосервисами |
| `notify_recipients` | Чаты мастеров для уведомлений | удаляются при смене бота |
| `clients` | Клиент автосервиса: Telegram ID, имя, телефон | уникален в пределах автосервиса |
| `requests` | Заявка: номер, статус, услуга, ответы, сообщение, телефон, заметка | ответы — снимок «название поля → значение» |
| `conversations` | Состояние диалога чата | JSON, по строке на чат |

**Форма услуги** — список полей `{id, label, question, type, required, options}`. Типы: `text`, `number`,
`choice`. Форма хранится в JSON внутри услуги: её читают и пишут только целиком.

**Заявка хранит снимок ответов**, а не ссылки на поля. Владелец может менять и удалять услуги — старые заявки
от этого не меняются. Ссылка на услугу остаётся для справки и обнуляется при удалении услуги.

**Телефон** — не поле формы, а обязательная часть любой заявки: без него мастеру некуда звонить. Хранится в
виде `+79001112233`.

## 6. Диалог бота

Состояния: `idle → service → field → phone → confirm ⇄ edit`. Состояние чата лежит в `conversations`.

| Состояние | Ждём | Переходы |
| --- | --- | --- |
| `idle` | Свободный текст | LLM нашла услугу → `field`/`phone`/`confirm`; не нашла → `service` |
| `service` | Кнопку услуги или ещё один свободный текст | выбрана услуга → дальше по форме |
| `field` | Ответ на текущий вопрос | следующий недостающий вопрос, затем `phone` |
| `phone` | Контакт или номер текстом | `confirm` |
| `confirm` | «Отправить», «Изменить», «Отменить» | заявка создана → `idle`; `edit`; сброс |
| `edit` | Что изменить: поле, телефон, услугу | соответствующий шаг, потом снова `confirm` |

Правило движения одно: после каждого ответа бот ищет, чего заявке ещё не хватает — поля формы, телефона или
подтверждения — и спрашивает это. Поэтому правка поля, пропуск необязательного вопроса и новое обязательное
поле, добавленное владельцем посреди диалога, обрабатываются одним и тем же кодом.

**Где LLM.** Только пока услуга не определена: один вызов на свободное сообщение. На входе — каталог услуг с
полями и текст клиента, на выходе — JSON `{service, fields, phone}`. Услуги передаются под короткими номерами,
а не UUID.

**LLM не доверяем.** Номер услуги сверяется с каталогом, значения проверяются по типу поля (число, вариант из
списка), неизвестные поля отбрасываются, телефон нормализуется. Что не прошло проверку, бот спросит сам.
Сообщение клиента идёт в роли `user`; промпт запрещает исполнять инструкции из него. Худший исход подмены —
неверно предзаполненное поле, которое клиент видит на шаге подтверждения.

**Если LLM недоступна, не настроена или не поняла** — бот показывает кнопки со списком услуг. Диалог никогда
не блокируется из-за LLM.

**Ограничения.** Не больше 20 вызовов LLM в час на чат и 300 на автосервис; не больше 5 заявок в сутки от
клиента; сообщения бота укладываются в лимит Telegram (длинные ответы сокращаются в сводке, в заявке хранятся
целиком). Диалог, в котором сутки ничего не происходило, начинается заново.

## 7. Раннер ботов

- Каждые несколько секунд сверяет запущенные циклы опроса с таблицей `bots`: новый токен запускается, заменённый
  перезапускается, удалённый останавливается.
- Статус бота (`pending`, `running`, `error` с причиной: токен отозван, конфликт, нет связи) пишется в базу и
  показывается в кабинете.
- Сообщения одного чата обрабатываются по порядку, разных чатов — параллельно.
- Среди нескольких реплик опрашивает одна: лидер держит advisory-лок PostgreSQL на выделенном соединении.
- Обновление считается принятым, когда раннер запросил следующую порцию. Если процесс упал, теряются сообщения,
  уже взятые из Telegram, но ещё не обработанные (клиент повторит). Дубликатов заявок при этом не бывает:
  у черновика есть идентификатор, и повторная отправка возвращает уже созданную заявку.

## 8. Кабинет

| Экран | Назначение |
| --- | --- |
| Регистрация, вход | Аккаунт и название автосервиса |
| Онбординг | Токен бота → статус запуска → ссылка на бота, уведомления, услуги |
| Заявки | Вкладки по статусам со счётчиками, автообновление, «В работу» из списка; на телефоне — карточки |
| Заявка | Ответы формы, первое сообщение клиента, телефон-ссылка, действия, заметка мастера |
| Клиенты | Список и история заявок клиента |
| Услуги | Каталог, конструктор вопросов, порядок, включение |
| Автосервис и бот | Реквизиты, токен, статус бота, получатели уведомлений |

## 9. Безопасность

- Все данные кабинета отфильтрованы по автосервису владельца; чужие объекты отдают 404.
- Токен бота наружу отдаётся только в маске. В базе хранится открытым текстом.
- Ссылка подписки мастера содержит одноразовый код: после использования код меняется.
- Весь текст клиента экранируется перед отправкой в Telegram (HTML) и выводится в кабинете как текст.
- Ключ LLM один на установку и лежит в окружении сервера.

## 10. Наблюдаемость и показатели

Логи — JSON в stdout. Метрики отдаёт бэкенд на `/metrics` в формате Prometheus. Счётчики увеличиваются в коде в
момент события; состояние (сколько автосервисов дошло до какого шага, сколько заявок ждёт) читается из базы при
каждом опросе `/metrics`, поэтому одинаково на всех репликах — в запросах берите `max`.

MVP должен ответить на три вопроса. Ниже — показатели под каждый и что с ними делать.

### Приносит ли продукт пользу

| Показатель | Метрика | Как читать |
| --- | --- | --- |
| Воронка онбординга | `autoservices{stage}`: `registered` → `bot_connected` → `has_requests`; отдельно `notifications_on` | Большой разрыв между `registered` и `bot_connected` — владельцы не справляются с токеном. Между `bot_connected` и `has_requests` — бот подключён, но клиенты о нём не знают. `notifications_on` заметно меньше `bot_connected` — заявки некому увидеть вовремя |
| Заявки | `requests_created_total{autoservice_id}` | Главное число продукта. По автосервису видно, жив ли он: нет заявок неделю — пора звонить владельцу |
| Доля завершённых диалогов | `bot_drafts_total{event}`: `started`, `submitted`, `cancelled`, `wrong_service` | `submitted / started` — конверсия бота. Остаток после `submitted` и `cancelled` — клиенты, бросившие диалог молча: если их много, вопросов слишком много или они непонятны |
| Скорость реакции мастера | `request_reaction_seconds` — время от создания заявки до «взял в работу» или «отклонил» | Обещание продукта в одном числе. Смотрите медиану и 90-й перцентиль: часы — нормально, сутки — клиент уже ушёл |
| Зависшие заявки | `requests_overdue` — новые старше 24 часов; `requests_by_status{status}` | `requests_overdue > 0` — клиенту не перезвонили за сутки. Реакцию мастера гистограмма покажет, только когда он среагирует; зависшие видны здесь |
| Что стало с заявками | `request_status_changes_total{to}` | Много `rejected` — бот собирает не то; много `cancelled` — клиенты не дожидаются |

### Справляется ли LLM

| Показатель | Метрика | Как читать |
| --- | --- | --- |
| Доля распознанных сообщений | `bot_classified_total{result}`: `recognized`, `unknown`, `unavailable` | `recognized` — LLM выбрала услугу. `unknown` — не поняла (в том числе «что-то случилось» без деталей). `unavailable` — LLM выключена, ответила ошибкой или исчерпан лимит: клиенты выбирают услугу кнопкой |
| Ошибки выбора услуги | `bot_drafts_total{event="wrong_service"}` к `bot_classified_total{result="recognized"}` | Клиент нажал «Другая услуга» под первым вопросом. Растёт — правьте описания услуг: по ним LLM и выбирает |
| Сколько вопросов экономит LLM | `bot_form_fields_total{source}`: `llm` — заполнено из первого сообщения, `client` — отвечено в диалоге | Доля `llm` — та часть формы, которую клиенту не пришлось набирать. Правка ответа перед отправкой тоже считается как `client` |
| Доступность и скорость | `llm_requests_total{result}`, `llm_request_duration_milliseconds` | Ошибки и задержка провайдера. Клиент ждёт ответа бота всё это время |
| Стоимость | `llm_tokens_total{kind}`: `prompt`, `completion`; `llm_requests_total` | Умножьте на цену модели. `prompt` растёт вместе с каталогом услуг: он целиком уходит в каждый запрос |

### Работает ли система

| Показатель | Метрика | Как читать |
| --- | --- | --- |
| Есть ли опрашивающий процесс | `bot_runner_leader` (1 у лидера), `bot_runner_bots` | `sum(bot_runner_leader) == 0` дольше пары минут — ни один бот не отвечает клиентам. Самый важный алерт |
| Состояние ботов | `bots_by_status{status,reason}` | `status="error"`: `unauthorized` — владелец отозвал токен, `conflict` — бота опрашивает кто-то ещё, `unavailable` — нет связи с Telegram. `pending` дольше минуты — раннер не подхватил бота |
| Обработка сообщений | `bot_updates_total{kind}`, `bot_update_errors_total`, `bot_updates_dropped_total`, `bot_update_duration_milliseconds{kind}` | Ошибки и отброшенные — клиент получил «что-то пошло не так» или не получил ответа вовсе, в норме ноль. Длительность — сколько клиент ждёт ответа бота, вместе с LLM и Telegram |
| Доставка уведомлений мастеру | `bot_notifications_total{delivered}` | `delivered="false"` — мастер не узнал о заявке (например, заблокировал бота) |
| Вызовы Telegram | `telegram_requests_total{method,ok}`, `telegram_request_duration_milliseconds{method}` | Доля `ok="false"` по `sendMessage` — бот не может ответить клиентам. Длительность `getUpdates` — это long polling, её не смотрите |
| HTTP API кабинета | `http_requests_total{method,route,status}`, `http_request_duration_milliseconds{method,route}` | Ошибки 5xx и задержка кабинета |

Примеры запросов (MetricsQL, как в VictoriaMetrics из этого репозитория):

```promql
# конверсия бота за сутки
sum(increase(bot_drafts_total{event="submitted"}[1d])) / sum(increase(bot_drafts_total{event="started"}[1d]))
# доля сообщений, по которым LLM выбрала услугу
sum(increase(bot_classified_total{result="recognized"}[1d])) / sum(increase(bot_classified_total[1d]))
# 90-й перцентиль реакции мастера, в часах
histogram_quantile(0.9, sum(rate(request_reaction_seconds_bucket[7d])) by (vmrange)) / 3600
# ни один процесс не опрашивает Telegram
sum(bot_runner_leader) == 0
```

Чего здесь сознательно нет: метрик по каждому клиенту и по каждой услуге (слишком много рядов для MVP; заявки по
услугам видны запросом к базе) и аналитики действий в кабинете.

## 11. Итоги оценки

Проект оценивали четверо: продакт, архитектор, инженер по надёжности и безопасности, дизайн-ревьюер.
Архитектура и модель данных приняты без изменений. Ниже — что решено по открытым вопросам и находкам.

### Делаем в MVP

| Что | Почему |
| --- | --- |
| Заявка создаётся идемпотентно: у черновика есть свой идентификатор | Если заявка создалась, а состояние диалога не сохранилось, повторное «Отправить» создавало вторую заявку |
| Кнопки вопроса привязаны к полю, кнопки сводки — к черновику | Нажатие варианта из старого сообщения записывалось в текущий вопрос |
| Брошенный диалог сбрасывается через 24 часа, старые строки удаляются | Сообщение вернувшегося клиента записывалось ответом на старый вопрос; данные клиента не хранятся бессрочно |
| Выход из неверной услуги: кнопка «Другая услуга» под первым вопросом, слова «отмена», «передумал» | Ошибку выбора услуги было видно только на шаге подтверждения |
| «Привет» и «спасибо» обрабатываются без LLM | После «Заявка принята» на «спасибо» бот показывал список услуг |
| Первое сообщение клиента не затирается следующими | Мастер видел в заявке «диагностика» вместо описания проблемы |
| Лимит заявок — 5 за сутки на клиента по всем статусам; при отказе черновик сохраняется | Лимит «5 необработанных» обходился циклом «создать — отменить» |
| Потолок вызовов LLM на автосервис в час; слишком большой каталог в LLM не отправляется | Лимит был только на чат, расход на общий ключ ничем не ограничивался |
| Остановка: все боты останавливаются разом, на завершение обработки — ограниченное время | Последовательная остановка не укладывалась в отведённое время, очередь терялась |
| Паника в обработчике сообщения не роняет процесс | Один сбой останавливал ботов всех автосервисов |
| Повтор отправки при ответе 429 от Telegram | Подтверждение клиенту и уведомление мастеру терялись без повтора |
| Соединение с локом лидера с коротким TCP keepalive; лидерство теряется после нескольких неудачных проверок подряд | После жёсткого падения узла лок висел до двух часов, боты молчали |
| На фото и голосовое бот повторяет текущий вопрос | После отказа клиент не видел, на что отвечать |
| Описание бота в Telegram: название автосервиса, адрес, телефон | Клиент открывал пустого бота и не знал, куда пишет |
| Типовые услуги: убран вопрос о пробеге, вопрос о времени не обещает запись | Лишний шаг; клиент считал, что записан на названное время |
| Сессия кабинета 30 дней; после входа возврат на запрошенную страницу; сброс пароля командой сервера | Мастер каждый день входил заново и попадал не на ту заявку |
| Онбординг: уведомления мастеру — главный шаг; ссылки на бота и для мастера можно скопировать | Экран говорил «ничего настраивать не нужно», и заявки никто не видел |
| Кабинет на телефоне: телефон клиента — кнопка звонка вверху заявки; «Отклонить» с подтверждением; цели касания от 44 px; контраст от 4.5:1 | Главное действие мастера требовало прокрутки; необратимое действие срабатывало от промаха |

### Откладываем

- **Шифрование токенов ботов.** Ключ лежал бы рядом со строкой подключения к базе, а утечка базы и так раскрывает
  телефоны клиентов. Вернуться вместе с отдельной ролью базы и шифрованием бэкапов.
- **Доставка «хотя бы один раз».** При падении процесса теряются сообщения, уже взятые из Telegram, но не
  обработанные; клиент повторит. Дубликатов заявок нет.
- **Ограничение частоты регистрации и входа.** До публичного запуска — на обратном прокси.
- **Уведомление клиента о смене статуса, фото, несколько сотрудников, восстановление пароля по email, вебхуки.**
- **Тёмная тема.**

### Не делаем

- Часовые пояса в боте: дат бот не показывает.
- Экономию LLM кешированием или отдельным классификатором: хватает лимитов и списка коротких слов.
